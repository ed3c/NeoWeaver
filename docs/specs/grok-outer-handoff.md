# Grok → outer → 原 Noodle owner 的候選接線

本輪承接已確認的 Neo route，優先補 Grok 的結構化往返，再驗收 guest 品質與恢復。
其他 OpenShell 聊天只讀進度，未向其發訊息或修改其 checkout。
原 Host 仍不可用，原 persisted context 尚未 detached。這是原生執行的實際阻斷。

## 原 producer 與 Consumer

原 Loop inspect 提供 candidate／review_input。新 companion prepare 核對同一候選、
OpenShell runtime 及目前 Session 審查的必要功能證據，固定所選 Noodle set、
最小來源片段與原 UML queue。功能判斷由 Session 負責；來源綁定不認證其語義。

原 Noodle set 的本機 Grok CLI 消費提示詞資料，回傳 summary 及 evidence／metrics／
repair／policy／no_change 請求。請求包含原 queue command IDs、理由與要求的結果，
不接受可執行 argv。新 CLI journal 在模型呼叫前保存意圖。同一來源與並行重送
讀回原 capture；中斷且結果未知時不重跑模型。它不是另一份產品任務狀態。

Session 消費 response FileRef，判斷來源及原授權後提交 action。產品修正與角色
交接回原 candidate-review，保留原 role、寫入範圍、控制 ACK 與 next。
Grok 不改產品，不選 Poteto playbook。必要指標依原 Test Manager 與審查角色執行。
原 Noodle 產生新候選後，核對功能結果，再將新 candidate 與 previous response 交回審查。
缺必要證據不能由 no_change 轉成批准；圖形 policy 保留提案，不假冒已套用的事實。

## 指標與 UML 原始檔案讀回

原 supervisor 已封存並傳回整個 NOODLE_SESSION_DIR。審查角色將原始 JSON／EDN／文字
放在其 ub-review 子目錄。新 Reader 沿原完成 Reader 的 supervisor receipt 尋找
同一 session archive，核對原 bytes、大小與摘要，再保存有界 regular files。
這沒有新增傳輸或更換 carrier。路徑逃逸、symlink、重複名稱、超量及來源漂移會拒絕。
無審查檔案時保持 NOT_RUN。檔案取回後 quality_acceptance 仍是 UNKNOWN。
原工具執行、coverage、CRAP、重複、mutation 與排除理由仍需各自驗收。

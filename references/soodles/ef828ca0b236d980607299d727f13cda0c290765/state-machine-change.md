# 狀態機修改契約

## 目的與適用範圍

本契約規範如何修改 AGENTS.md、P-class 指引、CLI 狀態機及其敘述。
目的是讓原需求、Session 判斷、行為指引、程式轉移與效果證據一致。
它適用於跨 repository 的修改工作，不要求特定產品、迴圈或執行身分。
採用本契約不代表必須修改每一層；只修正有來源支持的落差。

Session 是目前執行工程判斷的主體。P-class 是指導 Session 行為的文字。
CLI 狀態機是依實際輸入、狀態及權限執行轉移的程式。
Owner 表示原資料、轉移或效果的責任來源，不表示必須另找一場 Session。
P-class 可以指示 Session 呼叫已有工具，不能自行成為 Runtime 狀態或效果證據。

本契約是修改原則的單一來源，不新增 Runtime gate、Manager、scheduler 或核准流程。
原任務的權限、驗收及合法續行仍有效。與適用契約矛盾時，查明來源與範圍，
不能用這份通用文件覆蓋特定效果邊界，也不能藉特例刪除原需求。

## 五項原則

| 原則 | 修改時必須保留的行為 |
| --- | --- |
| 純方法論 | 方法說明目的、適用問題、可推翻觀點、判別證據與退出條件。它不依賴某個案例答案或專案身分。只在具名未決語義需要時使用。 |
| 案例結合 | 案例與方法分開引用。Session 核對原問題與案例共享的機制、不同條件及反例，只遷移適用的方法動作。案例不提供新權限，也不把示範結論變成驗收答案。 |
| 固定迴圈 | 程式固定可由資料確定的入口、身分、必要證據、合法轉移、退出及續行。已有有效續行就消費原結果，不每輪重新選方法。缺事實先讀來源，未知效果先讀回。 |
| P-class 斷言 | 每項斷言指出具名條件、原來源、適用範圍與不成立時的處理。沿既有 schema 傳遞，指向原 CLI 的驗證或續行。語義判斷、機械驗證、實際效果三者分開。 |
| CLI 修正 | 在原 producer／validator／consumer 的最早實際斷點修正。保留原要求、身分、拒絕、恢復與續行，不用改寫 prompt 掩蓋程式落差。沒有具體落差就不為契約另造程式。 |

結構化分析與發散式模式識別共同產生可推翻的視角。
兩種解釋可以同時成立，圖形聚集或文字清楚都不能證明因果。
沒有能改變決策的新證據或可查證問題時，停止認知遞迴，繼續獨立的授權工作。
這個退出條件不關閉仍未完成的原需求。

## 修改與推論路徑

Session 在原任務記錄中保留以下對照，不新增平行狀態檔或強制表單。
先讀既有來源、相似實作及觀察。它們足以說明同一故障時，不重播工作來取得相同證據。

| 邊界 | Session 核對與修正的內容 |
| --- | --- |
| 原需求 → 當前主張 | 保存 Goal、條件、權限、完整驗收與來源。指出主張、必要前提及未知，不把歷史案例提升為當前義務。 |
| 主張 → P-class 條件 | 有真實未決語義才按需推論。保存替代視角、雙方推翻條件及最小判別證據。可由原資料唯一確定的選擇交原程式，不要求 Agent 重猜。 |
| 條件 → CLI 轉移 | 對照同一份 validated schema data、當前狀態與原 continuation。敘述要能追到 actor、輸入、檢查、狀態變更、效果及失敗路徑。方法名稱固定不證明問題分類正確。 |
| 轉移 → Consumer／效果 | 原 Consumer 消費原返回的輸入及續行。身分、引用、digest、命令與狀態由既有 producer 提供，不從敘述重建。依原 Runtime／Provider 讀回判斷實際效果。 |
| 觀察 → 修正 | 找到最早不成立的交接，修正其原責任來源及受影響敘述。保留失敗歷史和未知，驗證後消費原 Owner 的下一動作。 |

修改某一層時，核對它的上下游是否仍一致。
只改措辭不能修好錯誤轉移；只改程式也不能留下要求 Agent 走舊路的指引。
若只缺來源或觀察，先補該缺口；不要把未知判成產品缺陷或新增必跑的推論階段。
同一問題連續三次修正失敗後，保留失敗並重新檢查根本前提，不重試未變輸入。

## 斷言與續行的界線

Session 宣告的語義條件仍可能錯誤。CLI 只能驗證它有能力核對的資料與合法轉移。
格式有效、來源身分相符或狀態為 ready，不能單獨證明語義正確或操作完成。
具名條件通過後，Session 在既有授權內消費原 CLI 返回的動作及結果。
新權限、缺證據與未知效果仍沿原入口處理，不能靠斷言通過。

若原入口返回 executable continuation，保留它提供的命令、環境及必要輸入。
來源文件、案例與展示快照裡的命令不因此成為可執行續行。
若沒有可執行命令，Session 依原 operation 與資料完成授權內的工程工作，
不從名稱猜 shell 命令，也不因此停止所有獨立工作。
本契約不新增自然語言命令解析器、通用 dispatch 或另一份方法選擇表。

拒絕和未決狀態保留具體原因、原下一步及適用範圍。
未知寫入先沿原 Owner 讀回，再決定能否重試。不得換路徑繞過拒絕。
提示詞只有在下個合法 Consumer 需要新行為時才作必要變更。
沒有新指示不代表刪除原 Goal、輸入、約束或驗收。

## 驗證與完成

Test Manager 或專案既有測試責任入口選擇必要控制，本契約不另選一套測試。
有程式落差時，用能辨別該落差的正例、拒絕例及必要合法鄰例驗證。
已有證據只有在涵蓋同一版本、輸入與主張時才能重用。
沒有新程式變更或未解疑慮，不為文件命名擴張 full suite。

P-class 行為改變時，沿專案既有的條件審查、實際 Consumer 觀察與回饋入口驗證。
純敘述的清楚度審查與 Agent 行為證據分開；缺少能力就保留受影響主張為 unknown。
程式測試、Agent 回報及 Provider 效果各有覆蓋範圍，不能互相替代。
缺失資料不能填零，欄位數或 CLI branches 不能充當 Session 決策數。
不因檔案拆分或提示詞縮短，宣稱推論品質或成本改善。

完成時說明改了什麼、原落差、實際觀察、剩餘缺口與原續行的處理結果。
本地完成、安裝生效、發布及整體 Goal 完成分開報告。
文件被連結不證明已載入；既有 Session 的指引載入依原 Host 行為核對。

## 引用與專案套用

其他文件以「狀態機修改契約」連結本文件，並說明當前修改範圍。
跨 repo 引用使用實際可解析的 repository 路徑或版本化文件來源。
來源不可讀時明列缺口，不假裝已採用，也不把本機私人路徑當成通用接口。
既有版本綁定可用來保留修改時的來源；本契約不新增必填 runtime metadata。
引用文件只補專案接口、欄位、效果邊界與案例，不複製另一套通用規則。

## 擴展到其他 repository

每個 repository 保留自己的 Goal、語義、CLI、驗證與發布入口。
通用契約只共用修改原則。先選本次需要的依賴層，不以 repo 名稱固定模式。

| 依賴層 | 必要能力 | 不因此新增的依賴 |
| --- | --- | --- |
| 獨立採用 | 可讀取的契約版本，以及該 repo 的來源與驗證入口 | Soodles Runtime、LoopManager、Noodle 身分或常駐服務 |
| 選用審查／回饋 | 原 skill 及被選定的回饋 CLI；保留專案既有要求 | 不因使用 Manager 的文件或唯讀命令而啟動 worker |
| 委派執行 | 原 LoopManager request、選定模式的資料與合法 admission | 不自動執行所有 Managers、不新增 repo 專屬 daemon |

接入時，先取得原契約完整 commit 及原文 bytes，再建立本地可讀的版本引用。
尚未發布或需離線使用時，可以隨 repo 保存未改寫的版本快照。
快照來源記錄保留 repository、完整 commit、原路徑與工具計算的內容 digest。
這是文件發行來源，不是任務 admission、Runtime metadata 或語義正確性證明。
不要假造可下載的遠端 commit，也不要把移動中的 main 當固定版本。
快照必須保持原文；各 repo 的差異寫在自己的套用文件，不在快照內分叉規則。
更新時新增所選版本、核對 bytes、更新引用並保留可追溯的舊版歷史。
這項更新發生在文件維護與安裝時，不增加每次任務必跑的網路查詢。

AGENTS 與相關 P-class 入口引用同一份專案套用文件。
該文件指出版本來源、獨立使用路徑、可選迴圈及原驗證／發布責任。
專案已有的審查或效果限制保持有效；獨立採用不是取消既有要求的豁免。
來源不可讀只阻擋依賴該來源的主張，仍可繼續不依賴它的授權工作。

選用 LoopManager 時，adapter 只傳遞原 request，保留結果與拒絕。
原 CLI 驗證資料、來源及合法轉移，不保證「完整語義正確」。
`outer-only` 回傳來源綁定投影，不自動執行 Thinking Method。
`inner-only` 使用原 admission；`outer-inner` 在必要投影成立後交原 admission。
Session 只在真正未決語義上使用 Thinking Router。機械缺件與未知寫入先讀回。
Hook 需要實際原生事件，Cron 需要已授權排程，發布仍由原 Provider 接續。
三種模式不是三個必跑階段，也不要求所有 repo 採用同一執行模式。

跨 repo 交接保留上游成果及下游原 Goal、範圍與驗收。
只能沿已支援的原交接入口；不把 local-task 接口冒充任意 Issue 或 outer-only 的交接能力。
有資料依賴的階段等候必要成果成立，獨立部分才能並行。
本地 DAG 與雲端唯讀快照只展示證據；匯入或部署不授權執行，也不證明語義通過。

接入驗證分開核對版本快照、實際指引載入、adapter 到原 CLI 的正反控制與安裝讀回。
單元測試的假 launcher 不算原生 CLI；outer-only 通過也不證明 inner worker 已執行。
安裝後讀回實際入口、版本、檔案及原結果。保留前一版本，以原入口回復，不重播既有任務。
未測的模式保持未測，不為展示完整而啟動沒有原任務的 worker。

修改「狀態機修改契約」本身也遵守本契約：保留原要求，指出改變的原則與反例，
驗證受影響的引用及 Consumer，再發行新的明確版本。
不得用新版名稱抹除舊失敗，或以文件升版改寫既有任務的來源、權限與 receipts。
